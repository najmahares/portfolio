Agreement Risk Scanner

NLP-powered contract risk analysis. Read the fine print, in plain English.

Agreement Risk Scanner is a full-stack application that reads Terms of Service agreements and explains the risks hidden inside them. A traditional NLP pipeline classifies each clause against five contractual risk categories, aggregates findings into a weighted score, and returns plain-English explanations, actionable recommendations, and a downloadable report. Users can paste text, upload a PDF or DOCX, or one-click scan the live terms of TikTok, YouTube, and Instagram.

Overview

Agreement Risk Scanner is a supervised text classification product. The premise is that the clauses carrying the most legal consequence in a Terms of Service agreement are the ones written to be skipped, and that the gap is not access to information but access to a system that reads on the user's behalf. The product operationalizes that premise into a single flow: submit an agreement, receive a scored, clause-level risk report in plain language.

The system is split into two independently deployed services. A FastAPI backend handles authentication, clause extraction, ML inference, scoring, persistence, and URL scraping. A Next.js frontend handles document upload, PDF and DOCX parsing in the browser, dashboard rendering, plain-English toggles, and PDF report generation. Data is stored in PostgreSQL across four tables. The ML model is a scikit-learn Pipeline combining TF-IDF vectorization with a Linear Support Vector Machine, loaded at process start and served synchronously.

The product scope is deliberately bounded. It is not a legal advisory tool, not a contract comparison platform, and not a general-purpose LLM wrapper. It is a text classification product with an explanation layer and a security-hardened account system around it.

The Problem

Terms of Service agreements are structurally asymmetric. The clauses that matter most — termination rights, content removal authority, unbalanced delegation of control — are written in language optimized to be skipped. A user signing up for a new app faces a forty-page document they will not read, and the consequences of that choice only surface later.

Existing tools do not close the gap. Legal review services are priced for corporate contracts, not consumer terms. Chat-based assistants answer direct questions but do not read the document first. Browser extensions summarize but rarely classify. General content sites explain legal concepts but do not connect them to the specific clauses a user has already agreed to.

The opportunity is a system that reads the agreement, identifies the clauses that carry real risk, and explains each one in a sentence a non-lawyer can act on. This is a supervised text classification problem with a small, well-defined label space, which is why it is served better by a traditional NLP pipeline than by a generative model.

Architecture

Frontend. Next.js 16 with App Router, React 19, JavaScript. Route groups separate public routes from the authenticated app shell. Custom design system implemented in a single global stylesheet with CSS custom properties for color, spacing, radius, and typography. Auth state held in a React Context that wraps the app at the root layout. ProtectedRoute component gates any authenticated route and redirects unauthenticated users to login.

Backend. FastAPI 0.111 on Python 3.10. Layered architecture with separate directories for routers, services, repositories, schemas, models, and core. Dependency injection used for database sessions and the current user. All routes authenticate via a bearer scheme that decodes the JWT, validates type, checks the jti against the revoked-token table, and loads the user from the database.

Database. PostgreSQL with four tables: users, scans, clauses, and revoked_tokens. Scans store aggregate statistics (total clauses, flagged count, flagged percentage, high and medium counts, risk score). Clauses are child records scoped to their parent scan and store the clause text, category, priority, flag status, and reasoning. Cascade deletes remove clauses when a scan is deleted.

ML layer. A single scikit-learn Pipeline containing a TfidfVectorizer and a LinearSVC, serialized with joblib and loaded at process start. The vectorizer uses sublinear TF scaling and unigram features. The classifier is a linear SVM trained on labeled contractual clauses across five categories. Inference is synchronous and stateless; the loaded pipeline is a module-level singleton.

Infrastructure. Backend deployed on Render with a managed PostgreSQL instance. Frontend deployed on Vercel. Environment variables for the API URL on the frontend and for the database URL, secret key, and JWT key pair on the backend. Database schema created at process start via SQLAlchemy metadata, with column-level migrations applied idempotently for already-provisioned databases.

Engineering Deep Dive

Clause extraction. Raw agreement text is split into individual clauses before classification. The extractor operates on sentence and paragraph boundaries, discards fragments below a minimum length, and preserves ordering so that clause numbers match the source document. Each clause is passed to the model independently, which keeps inference costs proportional to document length rather than quadratic.

Classification and reasoning. The pipeline receives a clause string and returns a single integer label. That label is mapped through a fixed dictionary to one of the five risk categories. A rule-based layer then maps each category to a human-readable explanation and a priority level. This separation is deliberate: the model produces a classification, and the reasoning layer produces the explanation. The two are kept independent so the model can be swapped without rewriting the explanation logic, and vice versa.

Weighted risk score. The score is calculated after all clauses are classified. HIGH priority findings are weighted at three points each, MEDIUM at one, and FAIR at zero. The sum is normalized against the maximum possible score for the document — the total number of clauses multiplied by three — and scaled to 100. This prevents long agreements from receiving inflated scores simply because they contain more clauses, and makes scores comparable across documents of different lengths.

URL scraping. The one-click popular-agreement feature sends a URL to a dedicated backend endpoint. The server fetches the page with a bounded timeout, parses it with BeautifulSoup, and strips script, style, header, footer, and nav elements before extracting the visible text. This runs server-side specifically to avoid browser CORS restrictions. The extracted text is passed through the same analysis function used for pasted input, so there is one inference path regardless of source.

Session and token model. Login issues two tokens. The access token is a short-lived JWT signed with RS256 using an asymmetric key pair, carrying subject, jti, issued-at, expiry, and a type claim. The refresh token uses the same signing scheme with a longer expiry and a refresh type claim. The refresh endpoint validates the type claim, loads the user, and issues both a new access token and a rotated refresh token. Logout decodes the access token, extracts the jti, and inserts it into the revoked_tokens table. Every authenticated request checks that table before proceeding.

Password and account security. Passwords are hashed with Argon2id using time_cost of three, memory_cost of 65536 (64 MB), and parallelism of four. Password strength is enforced at the schema layer: minimum eight characters, at least one uppercase letter, one lowercase letter, one digit, and one special character, with a blocklist of common passwords. Failed login attempts increment a per-user counter, and after five failures the account is locked for fifteen minutes. The registration endpoint returns a generic failure message when an email is already registered, preventing attackers from enumerating valid accounts.

Rate limiting. slowapi provides per-IP rate limiting on authentication endpoints at five requests per minute. The limit is applied at the route level via a decorator and enforced by middleware. Rate limiting and account lockout operate independently: one bounds request volume per IP, the other bounds failed attempts per account.

Client-side document parsing. PDF and DOCX files are parsed in the browser before any network call. PDF text extraction uses pdfjs-dist to load the document, iterate each page, and concatenate text content. DOCX extraction uses mammoth to produce raw text from the archived XML. Both paths run against an in-memory ArrayBuffer, and the parsed text is then submitted through the same endpoint as pasted text, keeping the backend path uniform.

Upload validation. Before any parsing runs, uploaded files are validated in three steps: extension allowlist, file size ceiling, and magic byte inspection. The first four bytes of the ArrayBuffer are read and checked against known signatures for executables (MZ), PDFs (%PDF), and ZIP archives (PK, which covers DOCX). Files that do not match their declared extension are rejected. This prevents a renamed executable from reaching the parser.

Quality Assurance

Testing is organized in two layers: a pytest suite covering authentication and authorization behaviour against a test database, and manual end-to-end verification against the deployed frontend and backend.

Pytest suite. Tests run against an isolated database with fixtures for the FastAPI client and a verified authenticated user. Coverage spans six areas. Registration: valid signup, duplicate email rejection, weak password rejection. Authentication: successful login issuing both tokens, rejection of incorrect passwords, lockout after five failed attempts. Token lifecycle: refresh endpoint issuing new tokens, logout revoking the access token. Authorization: authenticated users cannot read or delete another user's scan. Rate limiting: sixth request to a limited endpoint returns 429. Scan behaviour: input size limits enforced at the schema layer.

Manual end-to-end verification. Every authenticated flow was verified against the deployed Render backend through Swagger UI, and against the deployed Vercel frontend through the browser. This includes registration, login, token refresh, one-click scan of a live third-party URL, PDF upload, DOCX upload, cross-user scan isolation on the history page, and PDF report generation.

Environment verification. Model loading was verified at process start on the deployed backend by confirming the pipeline loads without warnings and produces correct predictions for known inputs. Database column migrations were verified idempotently by inspecting the running schema and confirming no column is added twice across consecutive deploys.
